# AI教学助手系统用户研究计划

## 📋 研究概述

### 研究背景
AI教学助手系统是一个基于AutoGen多Agent协作的智能教学辅助平台，专门针对大学编程基础课程（C语言、Python）。系统通过6个核心AI Agent的协作，为学生提供个性化、渐进式的编程学习反馈，帮助教师提高教学效率。

### 研究目标框架

基于**技术接受模型（TAM）**和**设计思维理论**，本研究聚焦四个核心目标：

1. **需求验证**：确认我们对教师痛点和需求的理解准确性
2. **功能优化**：基于真实教学场景调整产品功能优先级
3. **价值评估**：评估AI辅助教学的实际价值和接受度
4. **障碍识别**：发现技术实施中可能遇到的教育和管理障碍

### 理论基础

本研究基于以下教育理论和研究方法：

- **技术接受模型（TAM）**：评估教师对AI教学工具的感知有用性和易用性
- **建构主义学习理论**：理解教师对学生学习过程的认知和期望
- **扎根理论（Grounded Theory）**：从访谈数据中发现教学痛点的深层模式
- **人本设计（Human-Centered Design）**：以教师实际工作流程为中心的设计验证

## 🎯 目标用户画像

### 主要目标用户：大学编程课程教师

**基本特征**：
- **教学经验**：3-15年编程教学经验
- **技术背景**：计算机科学或相关专业背景
- **课程类型**：C语言程序设计、Python基础、数据结构与算法
- **班级规模**：30-100名学生/班
- **技术态度**：对教育技术有基本了解，愿意尝试新工具

**教学痛点假设**（需验证）：
1. 批改工作量大，每周需处理150-300份代码作业
2. 错误类型重复，80%学生犯相同基础错误
3. 反馈不及时，人工批改需要2-3天
4. 难以提供个性化指导，特别是大班教学环境
5. 缺乏系统性的学生学习进度跟踪工具

### 用户细分策略

**按技术接受度分层**：
- **创新者（Innovators）**：2-3位，技术敏感度高，愿意试用Beta版本
- **早期采用者（Early Adopters）**：4-5位，关注教学效果改进
- **早期大众（Early Majority）**：3-4位，需要看到明确价值才会采用

**按教学场景分类**：
- **理论型课程**：重视概念理解和算法思维
- **实践型课程**：重视编程能力和项目经验
- **混合型课程**：平衡理论与实践

## 📚 研究方法设计

### 第一阶段：深度访谈研究（定性研究）

**研究设计**：基于**半结构化访谈**方法，结合**关键事件技术**

**样本设计**：
- **目标样本量**：12-15位教师
- **抽样方法**：目的性抽样 + 滚雪球抽样
- **覆盖范围**：
  - 3所不同层次大学（985/211、普通本科、应用技术大学）
  - 2种主要编程语言（C语言、Python）
  - 3个教学经验层次（3-5年、6-10年、10年以上）

### 第二阶段：焦点小组讨论（群体动力学研究）

**设计理念**：基于**社会建构主义理论**，通过群体互动发现集体共识和分歧点

**执行计划**：
- **场次**：3场焦点小组
- **规模**：每场5-6位教师
- **时长**：90-120分钟
- **主题设置**：
  - 第1场：教学痛点和需求探索
  - 第2场：AI教学工具期望和担忧
  - 第3场：系统原型评估和改进建议

### 第三阶段：教学场景观察（民族志研究）

**观察目标**：深入理解真实的代码批改工作流程

**观察计划**：
- **观察对象**：2-3位不同类型教师
- **观察时长**：每位教师2-3小时的批改工作
- **观察要点**：
  - 批改流程和时间分配
  - 决策过程和判断标准
  - 工具使用习惯和痛点时刻
  - 反馈撰写的思考过程

### 第四阶段：原型测试（可用性研究）

**测试设计**：基于**认知走查（Cognitive Walkthrough）**方法

**测试场景**：
1. **新手教师使用场景**：首次使用系统批改作业
2. **熟练教师使用场景**：在现有工作流中集成AI工具
3. **批量处理场景**：处理一个班级的所有作业提交

## 🗣️ 访谈指南设计

### 开场阶段（5-10分钟）

**建立信任关系**：
```
"感谢您参与我们的研究。我们正在开发一个AI教学助手系统，希望真正帮助像您这样的编程课程教师。今天的访谈没有对错答案，我们只是想了解您真实的教学体验和需求。"
```

**背景信息收集**：
- 教学经验和课程类型
- 班级规模和学生特点
- 现有教学工具使用情况

### 痛点探索阶段（20-25分钟）

**基于关键事件技术的提问**：

1. **工作流程探索**
   ```
   "能否详细描述一下您批改一次编程作业的完整过程？从收到学生提交开始，到给出最终反馈结束。"
   
   深挖提示：
   - 每个步骤大约需要多长时间？
   - 哪些环节让您感到最困扰？
   - 您是如何确保反馈质量的？
   ```

2. **痛点事件回忆**
   ```
   "请回想最近一次让您特别头疼的批改经历。当时发生了什么？您是如何处理的？"
   
   深挖提示：
   - 这种情况多久发生一次？
   - 您觉得理想的解决方案是什么？
   - 如果有工具能帮您解决这个问题，您最希望它有什么功能？
   ```

3. **个性化教学挑战**
   ```
   "在大班教学中，您如何为不同水平的学生提供个性化的学习指导？遇到过什么困难？"
   ```

### AI接受度探索阶段（15-20分钟）

**基于TAM模型的探索**：

1. **感知有用性探索**
   ```
   "如果有一个AI助手能够自动分析学生的代码并生成初步反馈，您觉得这对您的工作会有什么帮助？有什么担忧？"
   
   深挖维度：
   - 时间节省的价值
   - 教学质量的影响
   - 学生学习效果的期望
   ```

2. **感知易用性探索**
   ```
   "您理想中的AI教学助手应该如何融入您现在的工作流程？您最不希望它增加哪些额外的工作？"
   ```

3. **信任度和控制感**
   ```
   "如果AI给出的反馈与您的判断不一致，您会如何处理？您希望在多大程度上能够控制和调整AI的建议？"
   ```

### 功能需求验证阶段（15-20分钟）

**基于我们6个AI Agent功能的验证**：

1. **CodeAnalyzer功能验证**
   ```
   "我们设计了一个代码分析专家，能够检测语法错误、逻辑错误和代码质量问题。在您的教学中，这类分析的重要性排序是怎样的？"
   ```

2. **PedagogyExpert功能验证**
   ```
   "系统会根据教学法理论（如建构主义、最近发展区理论）来调整反馈策略。您在实际教学中是否有意识地运用这些理论？您觉得这种自动化的教学策略调整有用吗？"
   ```

3. **StudentProfiler功能验证**
   ```
   "系统能够分析每个学生的学习模式和进度。您现在是如何跟踪和了解学生个体差异的？这种自动化的学生画像对您有什么价值？"
   ```

### 系统演示和反馈阶段（10-15分钟）

**原型演示脚本**：
```
"现在我想向您展示我们系统的一个早期原型。请您想象这是您日常工作中的一个场景..."

[演示核心功能流程]

"看到这个演示，您的第一反应是什么？如果要在您的课堂中使用，您觉得还需要哪些功能？"
```

**关键观察指标**：
- 即时反应（惊喜、困惑、担忧）
- 提出的问题类型
- 主动参与程度
- 对具体功能的评价

### 结束阶段（5分钟）

**未来参与意愿**：
```
"如果这个系统开发完成，您是否愿意在自己的课程中试用？您觉得什么条件下您会考虑采用这样的工具？"
```

**推荐其他用户**：
```
"您能推荐其他可能对这个研究感兴趣的同事吗？特别是那些在编程教学方面有不同观点或经验的老师。"
```

## 🎯 用户招募策略

### 招募渠道设计

**1. 学术网络招募**
- 通过计算机教育相关的学术会议和论坛
- 联系各大学计算机学院的教学副院长
- 利用教育技术相关的微信群和QQ群

**2. 分层招募策略**

**创新者层（2-3人）**
- 目标：发表过教育技术相关论文的教师
- 招募语言："参与前沿教育技术研究，共同探索AI在编程教学中的创新应用"
- 激励：研究合作机会、论文共同发表可能性

**早期采用者层（4-5人）**
- 目标：有使用在线教学平台经验的教师
- 招募语言："帮助改进编程教学效率，为学生提供更好的学习体验"
- 激励：免费试用机会、教学改进建议

**早期大众层（3-4人）**
- 目标：传统教学方式为主但关注学生成效的教师
- 招募语言："了解新技术如何帮助解决传统教学中的实际问题"
- 激励：小额研究补贴、教学资源分享

### 筛选标准

**基本条件**：
- 3年以上编程课程教学经验
- 目前承担C语言或Python基础课程教学
- 班级规模在30人以上
- 有基本的计算机操作能力

**多样性保证**：
- 学校类型：985/211院校 40%，普通本科院校 40%，应用技术院校 20%
- 教学经验：3-5年 30%，6-10年 40%，10年以上 30%
- 性别比例：尽量保持合理的性别分布
- 地域分布：覆盖华北、华东、华南三个地区

### 激励机制设计

**非物质激励**：
- 研究报告分享：提供教学改进的数据洞察
- 专家网络：成为我们的教育顾问，参与产品设计
- 学术机会：协作发表教育技术相关论文

**物质激励**：
- 访谈补贴：200元/次（深度访谈）
- 焦点小组：300元/次
- 原型测试：150元/次
- 长期合作：月度顾问费1000元（2-3名核心用户）

## 📊 数据收集与分析框架

### 数据收集方法

**1. 多模态数据收集**
- **录音记录**：所有访谈和焦点小组全程录音
- **视频记录**：原型测试阶段记录操作过程和面部表情
- **屏幕录制**：记录用户与原型交互的完整过程
- **现场笔记**：研究员现场观察和感受记录
- **后续问卷**：访谈后24小时内发送补充问卷

**2. 结构化数据模板**

```
访谈记录模板：
- 基本信息：[姓名、学校、课程、经验年限]
- 痛点记录：[具体痛点、频率、影响程度、期望解决方案]
- AI接受度：[有用性感知、易用性感知、信任度、担忧点]
- 功能反馈：[对6个Agent功能的评价和建议]
- 关键引用：[原始语录记录]
- 研究员观察：[非言语信息、情绪变化、特殊反应]
```

### 定性数据分析方法

**基于扎根理论的主题分析**：

**第一轮编码：开放性编码**
- 逐句分析访谈转录稿
- 识别初始概念和类别
- 标记情感态度和关键观点

**第二轮编码：轴心编码**
- 将开放性编码的概念分组
- 建立类别间的关系
- 形成初步的主题框架

**第三轮编码：选择性编码**
- 确定核心类别和主题
- 构建理论模型
- 验证数据饱和度

**分析工具**：
- **NVivo**：定性数据分析软件
- **Miro/Mural**：概念映射和关系图绘制
- **Excel**：量化数据统计和趋势分析

### 分析框架设计

**1. 教学痛点分析维度**
```
痛点分类框架：
├── 工作负荷痛点
│   ├── 时间成本（批改时长、频率）
│   ├── 认知负荷（复杂度、重复性）
│   └── 质量压力（标准化、个性化冲突）
├── 教学效果痛点
│   ├── 反馈及时性（时延问题）
│   ├── 反馈质量（深度、针对性）
│   └── 学生参与度（积极性、理解度）
└── 管理协调痛点
    ├── 工具整合（平台兼容性）
    ├── 数据管理（记录、追踪、分析）
    └── 团队协作（与TA、同事的配合）
```

**2. AI接受度评估模型**

基于**技术接受模型（TAM）**的扩展框架：
```
AI教学工具接受度 = f(感知有用性, 感知易用性, 信任度, 教学价值观匹配度)

感知有用性：
- 时间节省程度
- 教学质量改进
- 学生学习效果提升
- 工作满意度改善

感知易用性：
- 学习成本
- 操作复杂度
- 集成难度
- 技术支持需求

信任度：
- 准确性信心
- 透明度满意度
- 控制感
- 隐私安全感知

教学价值观匹配：
- 教学理念一致性
- 师生关系影响
- 教育公平性考虑
- 专业发展兼容性
```

**3. 功能优先级评估框架**

```
功能价值评估 = 教学价值 × 使用频率 × 可替代性 × 实现可行性

评估维度：
├── 教学价值（1-10分）
│   ├── 解决痛点的直接性
│   ├── 教学效果改进程度
│   └── 学生受益程度
├── 使用频率（1-10分）
│   ├── 日常使用频率
│   ├── 季节性需求强度
│   └── 用户群体覆盖度
├── 可替代性（1-10分）
│   ├── 现有工具能否解决
│   ├── 手工操作的可行性
│   └── 其他方案的成本
└── 实现可行性（1-10分）
    ├── 技术实现难度
    ├── 资源投入需求
    └── 时间成本估算
```

## 🎨 原型演示设计

### 演示材料准备

**1. 教学场景剧本**

**场景一：新手学生的C语言基础练习**
```c
// 学生提交的代码（包含典型错误）
#include <stdio.h>
int main() {
    int a, b
    printf("请输入两个数:");
    scanf("%d %d", a, b);
    int sum = a + b;
    printf("和是: %d", sum);
    return 0;
}
```

**AI反馈演示**：
```
🤖 代码分析专家: 发现3个语法错误...
📚 教学策略专家: 学生处于C语言学习初期，建议采用鼓励+引导的反馈策略...
👤 学生画像专家: 基于历史表现，该学生在指针概念上较薄弱...
✍️ 反馈生成专家: 你好！看得出来你对基本的输入输出逻辑理解得很好...
```

**场景二：中等水平学生的算法优化**
```python
# 学生提交的冒泡排序实现（可以工作但效率低）
def bubble_sort(arr):
    for i in range(len(arr)):
        for j in range(len(arr)-1):
            if arr[j] > arr[j+1]:
                arr[j], arr[j+1] = arr[j+1], arr[j]
    return arr
```

**2. 交互式原型设计**

**教师工作台界面**：
- 待批改作业列表
- AI分析结果预览
- 反馈编辑和审核界面
- 班级学习进度仪表板

**演示流程**：
1. **作业接收**：展示系统如何自动接收学生提交
2. **AI分析**：实时演示6个Agent的协作过程
3. **反馈生成**：显示结构化的教学反馈生成
4. **教师审核**：演示教师如何审核、修改AI建议
5. **学生收到**：展示学生看到的最终反馈界面

**3. 对比演示设计**

**传统方式 vs AI辅助方式对比**：
```
传统批改方式：
⏰ 时间消耗: 5-10分钟/份作业
😓 认知负荷: 需要完全手工分析每个错误
📝 反馈质量: 依赖教师当时的状态和经验
📊 数据积累: 难以系统性记录学生进步

AI辅助方式：
⏰ 时间消耗: 2-3分钟/份作业（主要是审核时间）
🎯 认知负荷: 专注于教学策略而非重复性分析
📝 反馈质量: 结构化、个性化、一致性好
📊 数据积累: 自动跟踪学生学习轨迹
```

### 演示关键观察点

**认知反应观察**：
- **即时理解度**：能否快速理解AI分析结果
- **信任建立**：对AI判断准确性的初始反应
- **工作流适配**：与现有习惯的兼容程度

**情感反应观察**：
- **焦虑程度**：对被AI替代的担忧
- **兴奋程度**：对效率提升的期待
- **怀疑程度**：对技术可靠性的质疑

**行为观察**：
- **交互模式**：主动探索 vs 被动接受
- **提问类型**：技术细节 vs 教学价值 vs 实施担忧
- **参与深度**：表面了解 vs 深入讨论

## 📈 教学价值评估框架

### 评估维度设计

基于**柯克帕特里克四级评估模型**的教育技术版本：

**Level 1: 反应层（Reaction）**
- 教师对系统的即时满意度
- 学习和使用的意愿
- 推荐给同事的可能性

**Level 2: 学习层（Learning）**
- 教师对AI辅助教学理念的理解提升
- 教学技能和策略的改进
- 对学生学习规律认识的加深

**Level 3: 行为层（Behavior）**
- 教学方法的实际改变
- 工作流程的优化程度
- 与学生互动方式的改进

**Level 4: 效果层（Results）**
- 学生学习成效的提升
- 教师工作效率的改善
- 整体教学质量的提高

### 量化指标体系

**效率指标**：
```
时间节省率 = (传统批改时间 - AI辅助批改时间) / 传统批改时间 × 100%
目标：>50%

反馈质量一致性 = 同一类型错误反馈的标准差
目标：显著降低

批改频率提升 = AI辅助后批改频次 / 传统批改频次
目标：>150%
```

**教学效果指标**：
```
学生编程能力提升率 = (期末成绩 - 期初成绩) / 期初成绩 × 100%
对照组比较

学生学习参与度 = 作业提交率 + 主动求助频率 + 课堂参与度
多维度综合评估

错误重复率下降 = (AI辅助前重复错误率 - AI辅助后重复错误率) / AI辅助前重复错误率
目标：>30%
```

**满意度指标**：
```
教师满意度 = 教学体验满意度 + 工作负荷改善满意度 + 学生成效满意度
5点李克特量表评估，目标：>4.0

学生反馈满意度 = 反馈有用性 + 反馈及时性 + 反馈个性化程度
目标：>4.0

系统推荐净值(NPS) = 推荐者比例 - 批评者比例
目标：>50
```

## 🔍 风险管理与质量保证

### 研究风险识别

**用户招募风险**：
- **风险**：目标用户响应率低，样本代表性不足
- **缓解策略**：
  - 提前2周开始招募，预留时间调整策略
  - 准备多渠道招募方案和替代用户池
  - 建立激励机制梯度，提高参与吸引力

**数据质量风险**：
- **风险**：访谈深度不够，获得表面化信息
- **缓解策略**：
  - 访谈员培训，掌握深度提问技巧
  - 准备多层级问题和引导话术
  - 设立数据饱和度检查机制

**偏见风险**：
- **风险**：研究者偏见影响数据解释，确认偏误
- **缓解策略**：
  - 多人独立编码，交叉验证分析结果
  - 设立外部专家审查机制
  - 记录分析过程和决策依据

### 质量保证机制

**数据收集质量**：
- 所有访谈录音备份，确保数据不丢失
- 访谈后24小时内完成初步整理

**分析质量保证**：
- 使用NVivo等专业软件确保分析的系统性
- 建立编码一致性检查机制（Kappa系数>0.8）
- 定期进行分析进展汇报和讨论

**报告质量标准**：
- 遵循定性研究报告的学术标准
- 提供充分的原始数据支撑
- 结论与数据的逻辑链条清晰
